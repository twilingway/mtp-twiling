# Design

## Context

См. proposal.md. Оба координатора выполняют побочные действия через `sync()`, а `choose()` сочетает
направленную передачу с разрешением конфликтов. Google при выборе удалённой конфликтующей версии
может публиковать новую облачную ревизию. Общий контракт уже зафиксирован в
`src/model/cloud-sync.ts`.

## Goals / Non-Goals

**Goals:** единое сравнение, проверяемая направленная передача и статус фактически выполненной
операции при сохранении существующих защит ревизии, аккаунта, отмены и атомарного импорта.

**Non-Goals:** изменение OAuth, scopes, флагов подключения, протоколов хранения и физическая
очистка.

## Decisions

- `CloudComparison { local, remotes, checkedAt }` хранится в `status.comparison` отдельно от
  `conflict`. Опциональный `inspect()` читает данные и строит сравнение без вызовов publish, apply,
  accept и технических проб записи. Использование `sync()` для этой кнопки отвергнуто из-за
  существующих отправки и импорта. Локальное сохранение кэша чтения допустимо; sync association,
  digest принятой версии, `pendingChanges` и `lastSyncedAt` проверка не изменяет.
- Внутренний preview закрепляет удалённые ID/heads, локальную revision и поколение подключения. Эти
  данные не расширяют общий UI-контракт. Передача проверяет их заново. Проверка и передача
  используют существующее исключение одновременных операций и отмену; инспекция не запускает
  автоматическую передачу своим завершением. Ранее включённая автоматика сохраняет своё поведение.
- Опциональный `receive(id)` выполняет проверенное чтение и только локальный apply выбранной обычной
  версии. Для Google он не переиспользует ветку `choose(remote)`, которая публикует при конфликте.
  Получение не объявляет несколько облачных heads разрешёнными. Существующий `choose(local)`
  остаётся направленной отправкой; старый Google migration/resolve сохраняется отдельным явно
  подписанным путём. При отсутствии нового метода UI не подменяет его `sync()`.
- Для Receive сохраняются очередь контроллера, проверка локальной revision перед commit и внутри
  транзакции, сигнал отмены, receipt и существующий recovery. Статус операции формируется из её
  результата; `idle` и старая дата сами по себе не означают новый успех. Проверка использует
  `checkedAt`, передача — собственный подтверждённый результат.
- Чистые функции формируют summaries и сравнивают закреплённые версии. HTTP, часы, storage и import
  принадлежат существующим adapters/координаторам. React показывает сравнение и вызывает методы;
  решение о разрешении действия и подтверждении не переносится в view.
- `CloudSyncSettings` меняет только порядок карточек. `CloudProviderSettings` показывает локальную
  версию, список удалённых версий, направление, последствия получения и результат операции.
  Существующие `enabled`, `automatic`, режим клиента и credential не переписываются.

## Risks / Trade-offs

- [Изменение после preview] → повторные проверки в сервисе; устаревшее сравнение не даёт права на
  импорт или отправку.
- [Старая дата выглядит новым успехом] → отдельные сообщения проверки, передачи и неизвестного
  результата, без вывода успеха из одного `lastSyncedAt`.
- [Receive случайно публикует разрешение конфликта] → отдельный путь и тест отсутствия remote
  mutations, включая несколько Google heads.
- [Просмотр требует скачивания содержимого] → использовать существующие лимиты чтения и проверки;
  повреждённые/неполные данные не превращать в пустое успешное сравнение.

## Migration Plan

Изменение не требует миграции сохранённых настроек. Сначала реализуются методы провайдеров и
проверяются побочные действия, затем подключается UI. Координатор выполняет общие проверки и
изолированную браузерную проверку. Откат UI сохраняет данные и настройки подключения.
