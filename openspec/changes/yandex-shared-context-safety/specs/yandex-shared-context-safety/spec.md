## Purpose

Сохранять актуальные данные при переключении между браузером и PWA одного профиля, не принимая
устаревшее состояние окна за новую пользовательскую правку.

## ADDED Requirements

### Requirement: Context-specific accepted baseline

Яндекс SHALL сравнивать состояние открытого окна с принятой этим окном базой; подтверждение другого
окна SHALL NOT превращать старое состояние в новую отправку.

#### Scenario: Unchanged background window

- **WHEN** окно A отправило новые настройки, а ранее синхронизированное окно B не изменялось
- **THEN** синхронизация B получает актуальные настройки без создания нового снимка и до экспорта
  устаревших настроек B

#### Scenario: Both windows edited

- **WHEN** после общей базы A отправило новые настройки, а B содержит самостоятельные правки
- **THEN** B показывает сравнение, сохраняя свои правки и облачные версии без автоматической
  отправки

#### Scenario: Delayed authorization

- **WHEN** B открылось с принятой P1, A отправило P2, а авторизация B завершилась позднее
- **THEN** B сохраняет базу момента открытия: неизменённое окно получает P2 без обратной отправки
  P1, а изменённое показывает сравнение

### Requirement: Guarded runtime refresh

Восстановление старого окна SHALL проверять аккаунт, сессию, поколение входа и локальную revision;
неизвестная история SHALL сохранять явный выбор направления.

#### Scenario: Refresh failure

- **WHEN** восстановление интерфейса не завершилось
- **THEN** окно сообщает ошибку, не экспортирует старые настройки и допускает повтор без облачной
  записи

#### Scenario: Unknown history

- **WHEN** окно не принимало облачную базу, даже если содержимое совпадает
- **THEN** требуется прежний явный выбор направления

#### Scenario: Default recovery after a failed shared refresh

- **WHEN** после сбоя восстановления общего runtime пользователь нажал обычную кнопку повтора
  восстановления
- **THEN** owner-scoped journal сохраняет режим shared refresh: canonical camera другого окна
  остаётся целой, а старый adapter не записывает её поверх актуальных данных

#### Scenario: Cold recovery and mode lifetime

- **WHEN** приложение перезапущено с незавершённым shared refresh
- **THEN** повтор того же owner читает прежний режим; другой owner его не наследует, а успешное
  завершение удаляет только запись своей операции

#### Scenario: Ordinary import recovery

- **WHEN** повторяется восстановление после обычного импорта
- **THEN** прежняя очистка shared-camera записей сохраняется и завершённый shared refresh не
  оставляет постоянный режим сохранения камеры

#### Scenario: Cold startup after native import commit

- **WHEN** приложение закрыто после native commit импорта и открыто заново до завершения
  восстановления
- **THEN** запуск обнаруживает owner-scoped receipt до загрузки графика и записи камеры,
  восстанавливает импортированные настройки без старой shared camera и очищает только свою запись
  после успеха
- **AND** при ошибке receipt и барьер записи сохраняются для повторного восстановления

#### Scenario: A new ordinary import commits before restoration fails

- **WHEN** после незавершённого shared refresh новый обычный импорт записан, но callback
  подтверждения, последующая проверка или восстановление завершились ошибкой
- **THEN** mode import и идентификатор native import уже сохранены атомарно вместе с данными;
  обычный и холодный retry очищают старую shared-camera запись без отдельной postcommit записи
  режима

#### Scenario: A new ordinary import does not commit

- **WHEN** запись receipt или данных нового обычного импорта прервана до native commit
- **THEN** данные и режим откатываются вместе, а прежний pending shared-runtime receipt сохраняется
