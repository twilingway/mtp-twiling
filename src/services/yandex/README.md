# Яндекс Диск: клиентский provider

Factory: `createTerminalYandexSync(host, config)` из `controller-yandex-sync.ts`. Общие UI/host и
публичная конфигурация принадлежат общему исполнителю. `resume()` запускает локальное чтение
сохранённых флагов; отключённый provider не вызывает OAuth или сеть. Native apply использует общий
host и точный `acceptedRevision` из commit callback.

OAuth-приложение зарегистрировано отдельным исполнителем. Публичный ClientID:
`5eb8206c526a4c5593716703d091fa8d`. Единственное право — `cloud_api:disk.app_folder`. Callback —
`/__dev/app/yandex-callback.html` на localhost/127.0.0.1:5290 и `/yandex-callback.html` на
`mtp-test.twiling.ru`/`mtp.twiling.ru`. Страница должна загружать обычный app shell; callback
обрабатывает включённый provider после готовности canonical workspace. Клиентский secret не нужен.

Authorization Code + PKCE S256, `state`/verifier в sessionStorage на 10 минут; URL очищается до
token exchange. Базовый account id/client id проверяется через Yandex ID без дополнительных profile
scopes. Access token хранится в отдельном AES-GCM vault, не связан с банком и не попадает в backup.
Используется исходный `expires_in`; недоказанный secretless refresh не реализован, истечение требует
нового явного входа. Официальные контракты: [PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url),
[базовый user info](https://yandex.ru/dev/id/doc/ru/user-information).

Файлы форматов v1 и v2 находятся в папке приложения `app:/mtp-yandex-v1`. Контейнер v2 содержит
текущую и, если она есть, предыдущую версию целиком. Каждая версия включает portable Backup2 и
бинарные изображения с SHA-256. ID и точные байты операции сохраняются до сети, account и credential
generation входят только в локальный журнал. Публикация использует временный файл, перемещение с
`overwrite=false` и проверку итоговых байтов. При первом подключении, включая пустой Диск,
пользователь выбирает направление. При автоматическом обмене известное облачное обновление
применяется, когда локальные данные совпадают с ранее принятой версией.

Обход использует только bounded headers: сначала 12 байт, затем точный размер JSON header. `Range`
применяется при поддержке сервера; ответ 200 читается до нужного префикса и отменяется. Полные тела
скачиваются только для выбранной версии и проверки текущих heads перед публикацией. Сводка header
проверяется по полным байтам перед принятием; исторические binary bodies не скачиваются ради списка.
Лимиты допускают до 10 000 файлов, 32 MiB новых headers за проход и 256 MiB на одну версию.
Контейнер v2 рассчитан на две версии и их заголовок. Превышение лимита даёт явную ошибку перед
очисткой.

После подтверждённой отправки и завершения очистки у клиента остаётся один физический контейнер v2 с
двумя полными версиями: текущей и предыдущей. Перед удалением fallback полностью проверяются обе
версии latest-контейнера; два контейнера сохраняли бы третью скрытую версию. Клиент проверяет
принадлежность и актуальность каждого старого контейнера перед точным удалением по MD5. Старые файлы
v1, файлы других клиентов, неизвестные форматы, временные файлы незавершённых операций и нерешённые
ветви защищены. Подтверждённая отправка сохраняет свой статус, даже если очистка ожидает повтора.
Повтор выполняется через синхронизацию. Сравнение и обычное получение версий не запускают очистку.

«Этот браузер» сохраняет UUID обычного клиента. «Тестирование» включает общий клиент, который можно
выбрать вручную или параметром `sync-client=testing`. Для нового сеанса DEV это режим по умолчанию.
Сохранённый выбор имеет приоритет. Приватный режим браузера автоматически не определяется.

Подтверждённые ссылки принятия сохраняют связь клиентов после очистки старых родителей. Повторная
синхронизация одинаковых проверенных данных не создаёт снимок и не требует нового выбора. Изменение
локальных данных, неизвестная ссылка либо нерешённые ветви сохраняют явное сравнение версий. Перед
отправкой вкладка сверяет сохранённый флаг включения; автоматическое задание также сверяет
автосинхронизацию. Выключение автоматики не запрещает явную ручную синхронизацию.

Перед native import сохраняется durable apply intent, commit callback синхронно фиксирует
acceptedRevision. Сбой UI restore после commit не повторяет native write при retry. После reload
совпадение canonical digest с целевой версией также позволяет завершить receipt без нового импорта;
при неясном или изменённом состоянии сохраняется indeterminate и требуется явный выбор.

Диагностика: `runTerminalYandexSyntheticProbe(provider, cleanup)` возвращает только проверенные
флаги и имя случайного probe-объекта. Не читает workspace; токен, account id и signed href не
выходят из closure. `cleanup=true` удаляет только собственный `probe_<uuid>.mtp` с MD5 guard;
обычные ревизии этот API удалить не может. Запускать после настоящего входа, без token logging.

Проверка live-95 прошла на одноразовых файлах с реальной авторизацией, readback, запретом перезаписи
и точным DELETE. Отдельная проверка трёх сохранений реального рабочего пространства подтвердила два
физических файла после очистки. Оба файла прочитаны и декодированы; текущие и предыдущие данные
совпали с исходным набором 20 инструментов и 2 рисунков, staging и пробники отсутствовали.
[Отчёт проверки](../../../openspec/changes/cloud-storage-retention/verification.md).

Если собственная отправка уже полностью записана в облаке, но подтверждение не дошло до журнала,
обычный sync проверяет точные байты CURRENT-снимка, account, поколение входа, устройство и
родителей. Он сначала сохраняет подтверждённый baseline, затем условно удаляет только
соответствующую попытку. Новые локальные изменения остаются dirty и отправляются отдельным обычным
снимком; импорта нет. Сравнение версий и явный выбор пользователя такое восстановление автоматически
не выполняют. В карточках повторяется ID браузера или подпись «Тестирование», чтобы две версии не
выглядели двумя разными устройствами.
